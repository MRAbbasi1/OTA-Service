# 2. DeviceType

Represents a class of hardware/software-compatible devices.

```text
DeviceType
────────────────────
id
code
name
platform
hardware_revision
description
is_active
created_at
updated_at
```

### Example

```text
code: bcs-controller-v1
name: OTA-Service device platform
platform: esp32-s3
hardware_revision: rev-a
```

### Path-bearing identity

`code` and `platform` are not merely descriptive metadata: they are the two
path segments of every OTA URL for that device type.

```text
{device_type} = device_types.code
{platform}    = device_types.platform
```

Consequences that are part of the domain rules:

* `code` matches `^[a-z0-9]+(-[a-z0-9]+)*$`, length 3–24, and is unique.
* `platform` matches `^[a-z0-9]+(-[a-z0-9]+)*$`, length 2–16.
* Creation validates the URL length budget, reserving version space:
  `len(code) + len(platform) <= 29`.
* Both fields are immutable once the device type has a registered device or a
  published release, because changing them would invalidate provisioned device
  URLs, signed manifests already in the field, and stored object keys.
* A release does not carry its own `platform`; it inherits the device type's.

Adding a new product family or a new platform is therefore a data operation — a
new device type — not a code or routing change.

The complete model is `docs/16-update-path-and-publication.md`.

# 4. Raw eFuse MAC

`raw_efuse_mac` represents the MAC value sent by `OtaManager` in:

```text
X-Device-Mac
```

This value must not be confused with the network MAC generated by the Ethernet layer.

The OTA documentation explicitly identifies the distinction between the raw eFuse MAC and the network-visible Ethernet MAC.

The database field must therefore use an explicit name:

```text
raw_efuse_mac
```

rather than simply:

```text
mac
```

# 6. FirmwareRelease

Represents a logical firmware release.

```text
FirmwareRelease
────────────────────
id
device_type_id

version
name
release_notes

status

created_by
created_at
published_at
updated_at
```

Platform, URL path prefix, and object key prefix are all derived from the
parent device type and are not stored on the release. The release's `version`
is stored as the bare numeric triple (`2.6.1`); the `v` prefix is a rendering
detail of the URL path and the object key only.

The sole release lifecycle is:

```text
UPLOADED
VALIDATED
DRAFT
PUBLISHED
DEPRECATED
ARCHIVED
```

---

# 7. FirmwareArtifact

Represents the actual binary stored in MinIO.

```text
FirmwareArtifact
────────────────────
id
release_id

storage_bucket
storage_key

filename
content_type

size
md5
sha256

created_at
```

The binary itself must not be stored in PostgreSQL.

`storage_key`, `filename`, `md5`, and `size` are all published facts: they are
covered by the manifest signature and are immutable after publication. `md5`
and `size` are always computed by the backend, never admin-supplied, and the
`size` must be in the range the device parser accepts (1 byte – 4 MiB).

---

# 7.1 FirmwareManifest

Represents the signed manifest that is actually served to devices, and the
validated field set recorded at publication time.

```text
FirmwareManifest
────────────────────
id
release_id
artifact_id

version
url
md5
size
signature

storage_key
manifest_sha256

signature_source         # UPLOADED | GENERATED
validated_at
created_at
```

`url` is composed by the backend from the device type code, platform, version,
and filename; it is never accepted from an upload. It is signed as part of
`version|url|md5|size`, so a disagreement between the stored manifest and the
stored artifact is an integrity failure rather than a metadata discrepancy.

The stored object holds the exact published bytes, and the served response must
be byte-identical to it.

---

# 8. Relationship

```text
DeviceType
    |
    +---- Device
    |
    +---- FirmwareRelease
              |
              +---- FirmwareArtifact
              |
              +---- FirmwareManifest
```

A device never receives a release from another device type. The device type is
therefore the scope of the firmware catalog, the OTA path, and every update
policy that is not device-specific.

```text
ends_at nullable

```

The first implementation should support:

1. Default behavior
2. Device-type policy
3. Device-specific policy

A generalized rule engine is intentionally deferred.

# 10. Policy Targeting

Policy specificity should determine precedence.

Recommended order:

```text
Device-specific
      ↓
Device-type
      ↓
Global default
```

If multiple policies of the same scope apply, explicit priority must resolve the conflict.

The implementation must never rely on database row ordering.

# 11. UpdateAttempt

Represents a server-observed update operation.

```text
UpdateAttempt
────────────────────────
id
device_id
release_id

from_version nullable
from_version_source nullable
to_version

status
failure_reason

started_at
completed_at

attempt_number
created_at
```

Recommended statuses:

```text
CHECKED
UPDATE_OFFERED
DOWNLOAD_STARTED
DOWNLOAD_SERVED
DOWNLOAD_FAILED
```

`DOWNLOAD_SERVED` means the server completed its response stream; it does not
mean that the device installed or booted the image. The current OTA protocol
does not permit `VERIFIED`, `SUCCESS`, or any installed-and-booted state.

# 14. Version Model

Firmware versions shall use the firmware-compatible Semantic Versioning subset:

```text
MAJOR.MINOR.PATCH
```

Each component is a non-negative decimal integer; pre-release and build suffixes
are not supported. Versions must be parsed and compared numerically.

String comparison must never be used for firmware eligibility.

# 15. Domain Invariants

### Device

* serial number must be unique
* raw eFuse MAC must be unique
* device type must exist
* only `ACTIVE` devices with `ota_enabled=true` can receive an OTA offer
* known firmware version and server-served download version are distinct facts
* a device is only ever offered firmware belonging to its own device type, and
  its OTA path identity (`code`, `platform`) is its device type's

### Firmware

* version must be valid (`MAJOR.MINOR.PATCH`, numeric only, under 16 characters)
* release must reference a valid device type
* published releases must have a valid artifact
* published artifacts are immutable
* a release's platform is its device type's platform; a release never carries an
  independent platform value
* the composed manifest `url` must be under 96 characters, and the composed
  `url` is the only URL any device is ever given
* the manifest `url` must be byte-identical to the URL the platform serves, and
  a device's requested path identity must match the authenticated device type
* the served manifest must be byte-identical to the validated stored manifest
* a device type's `code` and `platform` are immutable once the type has a
  registered device or a published release

### Policy

* target version must belong to the same device type
* downgrade is forbidden for the current firmware; `allow_downgrade` is future metadata only
* conflicting policies must be resolved deterministically
* a policy affects eligibility only; it never changes a device's OTA path,
  URL structure, or device type

# 16. Update Decision Model

The central domain operation is:

```python
resolve_update(device) -> UpdateDecision
```

Conceptually:

```text
Device
  |
  v
Is device active?
  |
  v
Is OTA enabled?
  |
  v
Resolve applicable policy
  |
  v
Find published compatible releases
  |
  v
Apply policy constraints
  |
  v
Select target release
  |
  v
Return UpdateDecision
```

---

# 17. UpdateDecision

A decision object should contain enough information for both the OTA API and Dashboard.

Conceptually:

```text
UpdateDecision
────────────────────
device_id
current_version

update_available
target_version

reason
policy_id

allow_downgrade
```

Possible reasons:

```text
NO_UPDATE
LATEST_AVAILABLE
PINNED_VERSION
VERSION_RANGE
OTA_DISABLED
DEVICE_INACTIVE
NO_ELIGIBLE_RELEASE

```

The exact enum should be finalized during implementation.
