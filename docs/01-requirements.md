# OTA Management Platform — Requirements

## 1. Functional Requirements

### FR-001 — Device Type Management

The system shall support management of device types.

A device type shall identify at minimum:

- code
- name
- platform
- hardware revision
- description
- active/inactive state

Example:

```text
Code: bcs-controller
Name: OTA-Service
Platform: ESP32-S3
Hardware Revision: Rev-A
```

---

## 2. Device Management

### FR-010 — Register Device

An administrator shall be able to create a device.

A device shall contain:

- device type
- serial number
- raw eFuse MAC
- authentication credential
- firmware state
- active state
- OTA enablement state
- timestamps

The current OTA protocol does not report the running firmware version. Any
known firmware version must carry its source; a served firmware download must
not be recorded as an installed version.

---

### FR-011 — Device Identity

The system shall uniquely identify a device using its registered identity.

The OTA identity consists of:

```text
Serial Number
Raw eFuse MAC
Device Token
```

The raw eFuse MAC is the MAC value used by the current `OtaManager`.

It must not be confused with the network MAC generated by `EthernetManager`.

---

### FR-012 — Device Token

The system shall support:

- token generation
- token rotation
- token revocation
- token activation/deactivation
- token usage tracking

Raw token values must not be displayed after initial issuance.

The database should store a secure representation rather than plaintext credentials.

---

### FR-013 — Device Activation

An administrator shall be able to:

- activate a device
- deactivate a device
- disable OTA for a device

An inactive or OTA-disabled device shall not receive firmware updates.

---

## 3. Device Status

The system shall track independently:

```text
registered_at
last_seen_at
last_manifest_check_at
last_update_started_at
last_update_completed_at
```

These timestamps must not be treated as interchangeable.

---

## 4. Firmware Management

### FR-020 — Upload Firmware

An authorized administrator shall be able to upload a firmware binary together
with its signed manifest.

The backend shall parse the uploaded manifest and record its fields:

- version
- url
- md5
- size
- signature

The backend shall calculate, from the binary itself:

- file size
- MD5
- SHA-256

The administrator must not manually provide size, MD5, SHA-256, or the download
URL.

The uploaded manifest is verified against the binary and against the URL composed
by the backend; a disagreement is rejected. The manifest's fields must be
byte-identical to the values the platform serves.

### FR-020a — Derived Update Path

Every device-facing URL shall be derived from validated data, never accepted as
administrator input:

```text
{device_type} = device type code
{platform}    = device type platform
{version}     = release version, rendered with a v prefix in the path only
{filename}    = the artifact filename
```

Creating a release shall provision the artifact and manifest objects at keys
that mirror the download URL, so that the URL, the storage key, and the release
metadata are the same fact expressed three ways.

---

### FR-021 — Store Firmware

Firmware binaries and their signed manifests shall be stored in MinIO.

PostgreSQL shall store only artifact and manifest metadata and the MinIO object
references.

Object keys shall be deterministic and shall mirror the public download URL
path.

---

### FR-022 — Firmware Release

A firmware release shall contain:

- device type
- version
- release name
- release notes
- release status
- publication timestamp
- creator
- artifact reference
- manifest reference

A release shall not carry its own platform; platform is inherited from the
release's device type, so the URL path has a single source of truth.

A release shall expose, for operators: the composed download URL, the composed
manifest URL, the storage keys, and the exact manifest bytes that will be served.

---

### FR-023 — Release Lifecycle

A release shall have a controlled lifecycle.

Recommended states:

```text
UPLOADED
VALIDATED
DRAFT
PUBLISHED
DEPRECATED
ARCHIVED
```

Only `PUBLISHED` releases are eligible for normal OTA delivery.

---

### FR-024 — Firmware Integrity

Every artifact shall have:

```text
size
md5
sha256
```

MD5 is required for compatibility with the current firmware implementation.

SHA-256 is maintained for stronger backend-side integrity verification.

---

## 5. OTA Manifest

### FR-030 — Manifest Endpoint

The backend shall expose the manifest endpoint required by the existing `OtaManager`:

```http
GET https://api.ota-service.example/api/v1/firmware/{device_type}/{platform}/manifest.json
```

This absolute URL is what is provisioned on each device as `OTA_ONLINE_URL`, so
the platform shall expose the derived value to operators at registration time.

The endpoint shall authenticate the device using:

```text
X-Device-Serial
X-Device-Mac
X-Device-Token
```

The endpoint shall verify that the requested device type and platform are the
authenticated device's own, and shall return the no-offer response otherwise.

The endpoint shall serve the stored, signed manifest bytes verbatim, with an
exact `Content-Length` and no redirect.

---

### FR-031 — Manifest Content

The response shall contain:

```json
{
  "version": "...",
  "url": "...",
  "md5": "...",
  "size": 123,
  "signature": "..."
}
```

---

### FR-032 — Manifest Signature

The signed payload format is exactly:

```text
version|url|md5|size
```

The platform shall accept a manifest already signed by the release pipeline and
serve those exact bytes, and shall not be required to hold the signing private
key. If a deployment configures the firmware public key, the platform shall
verify the uploaded manifest's signature and reject it when verification fails.

Where the platform generates a manifest itself, the signature must remain
compatible with the public key embedded in the firmware, which the device uses
as the authoritative verifier.

---

## 6. Firmware Download

### FR-040 — Firmware Download

The backend shall serve firmware binaries through a controlled authenticated route:

```http
GET https://cdn.ota-service.example/firmware/{device_type}/{platform}/v{version}/{filename}
```

This URL is never provisioned on a device; it is issued inside the signed
manifest and requested verbatim by the device.

The device authentication mechanism shall apply to firmware downloads as well as
manifest requests, and entitlement shall be re-resolved per download rather than
inherited from having served the manifest.

The delivery hostname shall be served by this application, shall never expose
MinIO, and shall never answer with a redirect.

---

### FR-041 — Content-Length

Firmware responses must provide an accurate `Content-Length`.

The backend shall not rely on chunked transfer encoding for the current device contract.

---

### FR-042 — HTTP Status Semantics

The backend shall preserve the device-side interpretation of HTTP responses.

```text
200 → success
401 → authentication failure
403 → device not entitled
other 4xx → non-retryable
5xx → retryable
```

A transient backend failure must not be represented as a non-authentication 4xx response.

---

## 7. Update Policies

### FR-050 — Default Behavior

If no restrictive policy applies to a device, the device shall normally receive the newest eligible published firmware release compatible with its device type.

---

### FR-051 — Device-Specific Policy

The system shall support policies targeting an individual device.

---

### FR-052 — Device-Type Policy

The system shall support policies targeting a device type.

---

### FR-053 — Version Pinning

A policy shall be able to pin a device or target group to a specific firmware version.

Example:

```text
Device 10432
Target: 2.5.8
```

The device must not automatically receive 2.6.0 or newer while the pin remains active.

---

### FR-054 — Version Range

The system shall support minimum and maximum eligible versions.

---

### FR-055 — OTA Disable

A policy shall be able to disable OTA for a target.

For the current firmware, an OTA-disabled or otherwise no-offer device uses
the platform's documented 404 no-offer response, not 403.

---

### FR-056 — Downgrade Protection

Downgrade must not occur. The current firmware accepts only strictly newer
versions; a future downgrade feature requires a firmware protocol change.

### FR-057 — Update Path Categorization

The system shall support categorizing firmware by device type and platform, so
that each product family and each platform has its own release catalog, its own
URL prefix, and its own storage prefix without code changes.

Adding a product family or a platform shall be a data operation (creating a
device type), not a code change.

Existing device type codes and platforms shall be immutable once a device is
registered or a release is published.

---

## 8. Update Decision

### FR-060 — Deterministic Decision

The backend shall expose a single domain service responsible for determining
the target firmware. It may use known firmware state when available but cannot
derive the device's running version from the current OTA request.

Conceptually:

```text
Device
  ↓
Applicable Policies
  ↓
Eligible Releases
  ↓
Target Release
```

The decision must be deterministic.

---

## 9. Update Tracking

### FR-070 — Update Attempt

The system shall record OTA-related server-side events.

At minimum:

- device
- release
- source version
- target version
- start time
- completion time
- status
- failure reason

---

### FR-071 — Device Update Verification

The backend shall distinguish between:

```text
download served successfully
```

and:

```text
firmware successfully installed and booted
```

The second state cannot be claimed unless the device reports it.

The current `OtaManager` contract does not provide sufficient post-reboot telemetry to guarantee this distinction.

---

## 10. Dashboard Requirements

### FR-080 — Fleet Overview

The dashboard shall show:

- total devices
- active devices
- inactive devices
- devices by firmware version
- devices by type
- recent checks
- update activity
- failures

---

### FR-081 — Device List

The dashboard shall support:

- filtering
- sorting
- searching
- pagination

Filters should include:

- device type
- firmware version
- active state
- OTA state
- update policy
- last check status

---

### FR-082 — Device Detail

Device detail shall display:

- identity
- device type
- firmware
- OTA state
- policy
- registration date
- last check
- last update
- audit history

---

## 11. Audit

### FR-090 — Administrative Audit

The system shall record security-sensitive administrative actions.

Examples:

```text
device_created
device_updated
device_disabled
token_created
token_rotated
token_revoked
firmware_uploaded
firmware_published
firmware_archived
policy_created
policy_updated
policy_deleted
```

Audit records shall include actor, resource, action and timestamp.

---

# Non-Functional Requirements

## NFR-001 — Security

Secrets must not be stored in source control.

Sensitive credentials must be protected at rest.

Admin endpoints require authenticated access.

Device endpoints require device authentication.

---

## NFR-002 — Availability

A temporary MinIO or database issue must not corrupt firmware metadata or device state.

---

## NFR-003 — Integrity

Firmware artifacts must be immutable after publication.

Changing a published artifact without creating a new release must be prohibited.

---

## NFR-004 — Observability

The application shall provide structured logs and health/readiness endpoints.

---

## NFR-005 — Testability

Core domain logic must be testable independently of HTTP and infrastructure.

---

## NFR-006 — Compatibility

The implementation must remain compatible with the current `OtaManager` wire-level contract unless a documented protocol version change is introduced.

This includes the derived URL model: the manifest URL provisioned on devices,
the signed `url` field, the absence of redirects, and the absence of chunked
encoding are all part of the contract. `docs/16-update-path-and-publication.md`
is normative for them.

---

## NFR-007 — Scalability

The architecture must support future fleet growth without requiring immediate migration to microservices.

---

## NFR-008 — Maintainability

Business rules must not be embedded directly in route handlers.

---

## NFR-009 — Deployment

All production components must be reproducible through version-controlled configuration and Docker-based deployment.

---

## NFR-010 — Backup

PostgreSQL data and firmware artifacts shall have independent backup strategies.
