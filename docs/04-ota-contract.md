# OTA Management Platform — OTA Protocol Contract

## 1. Purpose

This document defines the server-side contract required by the current ESP32-S3 `OtaManager`.

This contract must be treated as a compatibility boundary between firmware and backend.

Changes require explicit review of both backend and firmware.

---

# 2. Device Authentication

Every OTA request must contain:

```http
X-Device-Serial: <serial>
X-Device-Mac: <raw eFuse MAC>
X-Device-Token: <device token>
```

The MAC must match the raw eFuse MAC stored for the device.

It must not be compared against the network MAC generated by the Ethernet layer.

---

# 3. Manifest Endpoint

Canonical route:

```http
GET https://api.ota-service.example/api/v1/firmware/{device_type}/{platform}/manifest.json
```

`{device_type}` is the device type code and `{platform}` its platform. Both
are derived from the authenticated device's own device type; a request naming a
different device type or platform receives the no-offer response, never a
manifest. The path parameters and their validation are specified in
`docs/16-update-path-and-publication.md` §3.

This absolute URL is provisioned on the device in NVS as `OTA_ONLINE_URL`.

Authentication is mandatory.

---

# 4. Successful Manifest Response

HTTP:

```text
200 OK
```

Required headers:

```http
Content-Type: application/json
Content-Length: <accurate byte length>
```

Required JSON fields:

```json
{
  "version": "2.7.0",
  "url": "https://ota.example.com/firmware/...",
  "md5": "...",
  "size": 1240720,
  "signature": "..."
}
```

The current device parser expects these keys.

---

# 5. Signature Payload

The exact signed payload is:

```text
<version>|<url>|<md5>|<size>
```

No additional whitespace or fields may be introduced.

`size` must be represented as an unsigned decimal integer.

---

# 6. Signature

The signature is authored by the **release pipeline**, which signs the SHA-256
digest of the payload with the OTA signing private key, and the platform stores
and serves those exact bytes.

The device verifies the signature using the embedded public key. The device is
the only verifier this contract requires; the server needs neither the private
key nor the public key for the normal flow.

The private signing key must never be embedded in firmware, must never be stored
in the application image, and is not required by the OTA service. A deployment
may configure the firmware public key to have the service additionally verify
signatures before accepting a release, in which case verification is mandatory
for uploads (`docs/15-implementation-decisions.md` §6).

---

# 7. Firmware Endpoint

Canonical route:

```http
GET https://cdn.ota-service.example/firmware/{device_type}/{platform}/v{version}/{filename}
```

This URL is never provisioned on a device. The device requests it verbatim,
exactly as received in the manifest `url` field.

`cdn.ota-service.example` is a delivery hostname of this same application, not a static
file server and never MinIO. The response must not be a redirect: the device
client does not follow `3xx` responses and would burn its retry budget instead.

`v` is part of the path only. The manifest `version` field and the signed
payload carry the bare numeric triple (`2.6.1`).

The request must contain the same device authentication headers, and the device
must additionally be entitled to the resolved release. Serving a manifest is
not an authorization grant for the binary.

Authentication is mandatory.

---

# 8. Firmware Response

Required:

```http
200 OK
Content-Type: application/octet-stream
Content-Length: <exact artifact size>
```

The Content-Length must exactly match the manifest `size`.

---

# 9. Transfer Encoding

The current firmware does not support chunked transfer encoding.

Therefore:

```text
Transfer-Encoding: chunked
```

must not be used.

---

# 10. HTTP Status Semantics

## 200

Successful request.

Manifest or firmware processing continues.

---

## 401

Invalid authentication credential.

The current device handles repeated authentication failures using a three-strike mechanism before its 24-hour automatic lockout.

Backend must use 401 for invalid authentication rather than device entitlement denial.

---

## 403

Unknown serial, raw-eFuse-MAC mismatch, or a known device in `DISABLED` or
`RETIRED` lifecycle state.

The current device immediately enters its 24-hour automatic lockout path.

Therefore 403 must be used carefully and only when the device is definitely forbidden.

---

## 404

An authenticated, otherwise active device has no firmware offer because the
requested path does not match its own device type or platform, OTA is
disabled, policy blocks it, or no eligible published release exists. This is
the platform's explicit no-offer response. The firmware does not retry it
until its next normal poll, and it does not enter the 24-hour lockout path.

The path-mismatch case is a provisioning defect rather than an entitlement
denial, which is why it does not use 403: entitlement is always decided against
the authenticated device's own device type, and a `403` would lock a
misconfigured device out of automatic checks for 24 hours. See
`docs/16-update-path-and-publication.md` §10.3.

A `200` manifest is returned only when an actual eligible release exists for
that device. The OTA request carries no running firmware version, so the
backend cannot construct a "not newer" manifest; the device's own behavior of
discarding a non-newer manifest is therefore not used as a backend response.
See `docs/16-update-path-and-publication.md` §10.4.

---

## 429

Rate limiting. It must never be replaced with 403. The firmware treats it as a
non-retryable response for the current poll, so limits must tolerate the
firmware's documented retry sequence.

---

## Other 4xx

The current firmware treats non-authentication 4xx responses as non-retryable.

Examples:

```text
404
410
422
```

must not be used for transient backend failures.

---

## 5xx

Server-side or transient infrastructure failure.

The current device treats these as retryable.

Examples:

```text
500
502
503
504
```

---

# 11. Firmware Artifact Requirements

Before publication the backend must validate:

```text
size
md5
sha256
device type
version
storage object
```

---

# 12. Artifact Immutability

Once a release is published:

```text
version
artifact
size
md5
sha256
```

must be immutable.

A modified binary requires a new release/version.

---

# 13. Manifest URL

The URL returned in the manifest is composed by the backend from validated
parameters — device type code, platform, version, and filename — and must
exactly equal:

```text
https://cdn.ota-service.example/firmware/{device_type}/{platform}/v{version}/{filename}
```

It must be an absolute URL, must be shorter than 96 characters, and must
resolve to a firmware endpoint accessible to the device. It must never expose
MinIO, and it must never redirect. The 96-character constraint applies to this
manifest `url`, not to the manifest URL provisioned in device NVS.

The URL is signed as part of `version|url|md5|size`, so it is never accepted
from an upload: an uploaded manifest whose `url` differs from the composed
value is rejected rather than stored. The length budget arithmetic and the
rejection codes are in `docs/16-update-path-and-publication.md` §§5 and 8.

The URL must correspond exactly to the artifact represented by:

```text
version
md5
size
```

---

# 14. Device Eligibility

A valid firmware release is not automatically eligible for every device.

Eligibility is determined by:

```text
device
device type
known firmware state, where available
device state
OTA state
update policy
release state
```

Only after eligibility is resolved may a manifest be generated.

---

# 15. Default Behavior

When no restrictive policy applies:

```text
latest published eligible release
```

shall be selected.

The system must not automatically downgrade a device.

---

# 16. Pinned Version

If a device is pinned to version `2.5.8`:

```text
Current: 2.5.7
Target: 2.5.8
```

If the device is already running:

```text
2.5.8
```

no update is offered.

If it is running:

```text
2.6.0
```

no downgrade is offered. The current firmware only accepts strictly newer
versions; `allow_downgrade` is future-only policy metadata.

---

# 17. Device Authentication Rate Limiting

The backend must independently rate-limit device OTA requests.

This is required because the current device-side 24-hour authentication lockout is RAM-only and is cleared by reboot.

Rate limits should consider:

```text
device
token
IP
endpoint
```

Use `429 Too Many Requests`, never 403. The exact initial limits and the
single-instance versus multi-replica implementation boundary are defined in
`docs/15-implementation-decisions.md`.

---

# 18. Security Requirements

OTA endpoints must use HTTPS in production.

HTTP support exists in the current firmware for fallback compatibility but must not be used for production deployment.

The backend must not disable manifest signature generation merely because HTTPS is enabled.

---

# 19. Compatibility Tests

The backend must include automated tests for:

```text
valid device
invalid serial
invalid MAC
invalid token
disabled device
OTA disabled
403 entitlement
401 authentication
published release
unpublished release
no newer version
pinned version
version range
Content-Length
manifest signature
firmware integrity
5xx retry semantics
```

The test suite must also cover the canonical serial and MAC normalization,
the explicit 404 no-offer response, 429 rate limiting, firmware field bounds,
path parameter derivation and its rejection cases, the manifest URL length
budget boundaries, byte equality between the stored and served manifest, the
device-type/platform path mismatch response, the absence of any redirect, and
a production-key signature conformance vector.

---

# 20. Contract Versioning

Future breaking changes shall introduce a new OTA API version.

Example:

```text
/api/v1/firmware/...
/api/v2/firmware/...
```

The backend must not silently change the meaning of an existing contract.
